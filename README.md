# PRÆTORE

[![Assurance gates](https://github.com/Mavericksantander/praetore/actions/workflows/assurance.yml/badge.svg?branch=main)](https://github.com/Mavericksantander/praetore/actions/workflows/assurance.yml)
[![Rust](https://img.shields.io/badge/Rust-core-000000?logo=rust)](https://www.rust-lang.org/)
[![Python](https://img.shields.io/badge/Python-bindings-3776AB?logo=python&logoColor=white)](https://www.python.org/)
[![PostgreSQL](https://img.shields.io/badge/PostgreSQL-replay%20adapter-4169E1?logo=postgresql&logoColor=white)](https://www.postgresql.org/)

**Deterministic authorization and governance primitives for AI agents and
autonomous systems.**

PRÆTORE evaluates signed authorization requests against declarative policy
and delegated authority, and records every decision as verifiable evidence.
Identity, authority, policy, decision and evidence stay separate concepts,
and a request that no rule covers is denied.

```mermaid
flowchart LR
    A[Agent] --> B[Authority]
    B --> C[Action]
    C --> D[Policy]
    D --> E[Decision]
    E --> F[Evidence]
```

> **Status:** under active development. Not independently audited or
> accredited. Passing the repository's tests is not a substitute for your own
> threat model, deployment validation and security assessment.

## Quickstart

Requirements: Rust 1.88 or newer and Cargo.

```sh
git clone https://github.com/Mavericksantander/praetore.git
cd praetore
cargo run -p praetore-core --example quickstart
```

Expected output:

```text
Strict: ALLOW; request intent, issuer authority, and evidence integrity verified.
HighAssurance: ALLOW; intent, issuer authority, attester signature, and evidence integrity verified.
```

The example creates an agent keypair, issues an authority bound to that key,
signs requests, evaluates them in **Strict** and **HighAssurance** modes and
verifies the resulting evidence. It uses ephemeral keys, an in-memory replay
guard and a demonstration freshness provider.

For the HighAssurance-only variant:

```sh
cargo run -p praetore-core --example high_assurance
```

## Third-party verification demo

One command signs a fictitious receipt, verifies it with public keys only,
then flips single bytes and shows each rejection:

```sh
./demo/verify-receipt.sh
```

![Real output of demo/verify-receipt.sh](docs/img/verify-receipt.svg)

- The keys come from a fixed, public seed: they are **DEMO/TEST-ONLY** and
  anyone can recompute them. Never sign anything real with them.
- The verifier receives only the public keys and key id, never a private key.
- Exit code is 0 only if the valid receipt verifies and every tampered copy is
  rejected with the expected error. CI runs it in `assurance.yml`.
- It proves the integrity of a historical record; it does not authorize
  anything.

Details: [`demo/README.md`](demo/README.md).

## Human approval with `praetore approve`

When a policy rule returns `RequireApproval`, the local reference gateway holds
the action. A human signs the approval challenge with a local Ed25519 approver
key; the action runs only after a separate `praetore dispatch`.

```sh
cargo build --locked -p praetore-cli        # binary: target/debug/praetore
praetore init ./praetore-local
cp crates/praetore-cli/examples/policies/require-approval.json ./praetore-local/policy.json
export PRAETORE_GATEWAY_DATABASE_URL='postgresql://<user>@127.0.0.1:<port>/<db>'   # local PostgreSQL
praetore doctor ./praetore-local
praetore run ./praetore-local                # terminal 1

praetore demo ./praetore-local set greeting hello                             # terminal 2
praetore approve ./praetore-local <request_id> --approver local-approver
praetore dispatch ./praetore-local <request_id>
```

![Real output of praetore approve](docs/img/praetore-approve.svg)

- `approve` recomputes the action digest and checks the policy digest before
  asking you to type `yes`. It refuses to sign on a mismatch.
- The gateway records the decision append-only and answers
  `approved_pending_dispatch`: the action has **not** run yet.
  `praetore dispatch` performs the single dispatch (here, `execution: confirmed`).
- The approval window is short (about 30 s in the local demo); after it the
  gateway answers `approval_expired`.
- All keys and tokens are generated by `init` for this demo only (**DEMO-ONLY**);
  this is not key custody or separation of duties.

Full guide: [`crates/praetore-cli/README.md`](crates/praetore-cli/README.md).

## Verify evidence offline

`praetore-verify` checks receipts without network access. The fixtures in
[`examples/verify/`](examples/verify/) use fixed, public, test-only keys
(generated by [`scripts/gen-verify-fixtures.sh`](scripts/gen-verify-fixtures.sh)).

```sh
cargo build --release --locked --package praetore-verify

# Valid receipt → {"ok":true,...}, exit 0
target/release/praetore-verify evidence \
  --evidence examples/verify/evidence.json \
  --attester-pin examples/verify/attester-public-key.hex \
  --issuer-pins examples/verify/issuer-pins.jsonl \
  --require-intent --format json

# Tampered receipt → {"ok":false,"command":"evidence","code":"EVIDENCE_FAIL"}, exit 1
target/release/praetore-verify evidence \
  --evidence examples/verify/evidence-tampered.json \
  --attester-pin examples/verify/attester-public-key.hex \
  --issuer-pins examples/verify/issuer-pins.jsonl \
  --require-intent --format json

# Policy digest, and a receipt required to record it
target/release/praetore-verify policy-digest --policy examples/verify/policy.json --format json
target/release/praetore-verify evidence \
  --evidence examples/verify/evidence.json \
  --attester-pin examples/verify/attester-public-key.hex \
  --policy examples/verify/policy.json --format json
```

Notes:

- The attester pin is the trusted Ed25519 public key as lowercase hex; issuer
  pins are JSON Lines of `TrustedAuthorityIssuer` documents. Both are
  provisioned separately from the evidence.
- The CLI never treats public keys inside evidence or authority documents as
  trust anchors. Invalid inputs return non-zero with stable reason codes.
- `--require-intent` requires `--issuer-pins`. `authority --agent` adds
  explicit subject-key binding for standalone authority documents.
- The fixture authority is valid from 2026-01-01 to 2036-01-01.
- The Python package is verify-only and calls the same Rust code
  (`praetore.verify_evidence_integrity`, `praetore.verify_evidence_attester_signature`).

## Core concepts

| Concept | Role |
| --- | --- |
| `AgentIdentity` | The entity requesting an action. |
| `Authority` | Capabilities, issuer, validity window and constraints granted to an agent. |
| `Action` | The requested operation: type, target, parameters. |
| `Policy` | Declarative rules evaluated against the action. |
| `Decision` | The outcome, with the contributing rules. |
| `Evidence` | Binds request, authority, action, decision and context into a verifiable record. |

**Precedence:** `DENY > REQUIRE_APPROVAL > ALLOW`. When several rules apply,
the most restrictive wins, independent of rule order.

**Fail closed:** when identity, authority, validity, constraint or policy
requirements are not met, the action is denied.

**Integrity:** evidence carries a SHA-256 context hash. The hash alone is not a
signature (anyone who can edit the document can recompute it); attester
signatures and signed intents use Ed25519. See
[crypto and policy semantics](docs/crypto-and-policy.md).

## Evaluation modes

| Mode | Intended use | Checks |
| --- | --- | --- |
| **Development** | Local development and compatibility | Allows unsigned authorities; no issuer pins, policy pin, attester, replay guard or freshness provider. Not an enforcement boundary. |
| **Strict** | Signature-checked offline evaluation | Signed authority from a pinned issuer, subject-key binding, signed agent intent. |
| **HighAssurance** | Strongest profile in this library | Strict plus v2 policy digest pin, audience- and expiry-bound intents, time-bounded authorities, attested evidence, digest-bound freshness with a capped lease, caller-owned replay guard. |

Use `AuthorizationEngine::production` for HighAssurance, or
`production_with_trusted_clock` when a fail-closed clock-health check is
required. The crate runs offline and in-process; it does not supply PKI,
revocation, a trusted clock, host isolation or atomic action execution.

## Current state on `main`

Merged features, each backed by code or tests in the repository:

- **Signed human approve/reject** (#14) — see
  [Human approval](#human-approval-with-praetore-approve) and
  [`crates/praetore-gateway/tests/enforcement.rs`](crates/praetore-gateway/tests/enforcement.rs).
- **Policy digest in the receipt** (#17) — `policy_digest` is bound into the
  evidence integrity hash and the attester signature; `Evidence::sign` refuses
  evidence without it; `Evidence::verify_policy` checks a receipt against a
  policy. See [`evidence.rs`](crates/praetore-core/src/evidence.rs).
- **Policy size and complexity limits** (#21) — an oversized policy is
  rejected at load time with `PolicyLimitExceeded`. Constants
  (`MAX_POLICY_RULES`, `MAX_CONDITIONS_PER_RULE`, `MAX_POLICY_TEXT_BYTES`,
  `MAX_CONDITION_STRING_BYTES`, `MAX_CONDITION_SET_VALUES`,
  `MAX_CONDITION_VALUE_DEPTH`) live in
  [`policy.rs`](crates/praetore-core/src/policy.rs). Raw JSON over 64 KiB or
  deeper than `MAX_JSON_DEPTH` fails closed with `PolicyEvaluationFailed`
  ([#23](https://github.com/Mavericksantander/praetore/issues/23)).
- **`PathPrefix` operator** — lexical, whole-segment path prefix
  (`/srv/agent` matches `/srv/agent/x`, not `/srv/agentx`). Values that are not
  absolute and normalized (`.`, `..`, `//`, `\`, NUL, `%`, relative paths)
  never match `Allow` and always match `Deny` / `RequireApproval`. Nothing is
  normalized (fullwidth dots, `∕`, `...` are ordinary characters). See
  [`tests/path_prefix.rs`](crates/praetore-core/tests/path_prefix.rs).
- **Tests ported from Canopy** — [`canopy_port.rs`](crates/praetore-core/tests/canopy_port.rs)
  rewrites the applicable cases of the earlier Canopy library as Rust tests,
  with default deny where Canopy allowed by default.
- **Gateway-executed sandbox** (Unix) — with `praetore init --sandbox-root`,
  the gateway itself performs `fs:write_file` / `fs:delete_file` through
  `SandboxDispatcher`.

Run the tests behind these items:

```sh
cargo test -p praetore-core --test canopy_port --test path_prefix --test path_prefix_followups
cargo test -p praetore-core --lib evidence::tests::policy_digest_is_bound_to_integrity_hash
cargo test -p praetore-gateway --test enforcement human_approval
```

## Limitations

- **Cooperative enforcement.** PRÆTORE governs only the actions submitted to
  it. It cannot stop an agent or process from acting directly.
- **Path checks are lexical.** `Prefix` / `PathPrefix` compare strings and
  never consult the filesystem. Symlinks are out of scope.
- **The journal does not independently confirm execution.** `executed` and
  `confirmed` record what the dispatcher adapter reported. A client that
  executes an action itself can leave a journal that does not reflect who ran
  it. The `praetore-exec-mode: gateway` header is a client declaration, not
  enforcement; OS-level isolation is still required.
- **Receipt deletion is not detectable by a third party.** Each receipt is
  signed on its own; nothing signs the journal sequence. See the
  [journal chain proposal](docs/proposals/journal-chain-jsonl.md).
- **No sustained fuzzing campaign.** CI runs each fuzz target as a short
  smoke test only.
- **Not a PKI, identity registry, revocation database, trusted clock, key
  management system or sandbox by itself.** Trust anchors, key custody,
  freshness, replay storage and host hardening remain deployment
  responsibilities. Read the [threat model](docs/threat-model.md) and the
  [pre-user deployment gates](docs/pre-user-pilot-gates.md) before any
  high-consequence pilot.

## What was and was not exercised

Run on Linux for this README revision: the quickstart example,
`./demo/verify-receipt.sh`, the `praetore-verify` commands above, and the CLI
flow `init` → `doctor` → `run` → `demo` → `approve` → `dispatch` against a

server-restart tests in
